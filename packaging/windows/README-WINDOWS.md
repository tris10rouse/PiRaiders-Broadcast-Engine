## Extract and configure a disposable workstation

The recorded evaluation build may be evaluated on a disposable, nonproduction Windows x64 PC (`OPERATOR-CHECKLIST.md`). On that PC or a developer bench, extract the entire ZIP into a new writable folder on nonproduction Windows x64; do not run inside the archive or overwrite an existing installation. No system Node/npm/PM2 or repository checkout is needed. Installed .NET Framework v4 is required for the containment host. Windows CI does not establish Windows10 target-PC or stadium compatibility.

Preserve `BUILD-MANIFEST.json`, the ZIP SHA-256 sidecar and all licenses. The unsigned manifest detects accidental drift, not download authenticity. Initial manifest verification must precede configuration: operator files and logs are intentionally absent from the original inventory. Run `Verify-PiRaiders.cmd` (no arguments, bundled Node only) from the extracted root before any configuration: it prints one line, `BUNDLE_VERIFIED`, or `BUNDLE_DIFFERS` with the kinds `missing`, `changed` and `extra` and their counts, or `MANIFEST_INVALID`; never a path. Steps and codes: `OPERATOR-CHECKLIST.md` step 1.

1. Copy `app/config/piraiders-app.example.json` to `app/config/piraiders-app.json`. This is machine-owned local configuration, not the Apps Script exchange. Configure separate catalog/media/cache/runtime roots; keep source media separate from private cache/runtime paths. Refer to the source repository's Game Day backend contract before adding an event.
2. If starting a disposable new SPX bench, copy `app/config/spx-app.example.json` to `app/config.json` and create `app/DATAROOT`, `app/LOG` and `app/events`. If using existing SPX, preserve its configuration/data and point `spxConfigFile` at the intended app-relative file. The launcher requires a bounded existing configuration with a valid explicit port and never generates or rewrites it. The blank credentials in the example are for an isolated bench; existing SPX login/configuration policy controls access. This package changes no firewall or network settings.
3. The example has `output.type:none`, loopback-only RossTalk and no events; the empty catalog is expected. It cannot produce video merely by launching. It has no `caspar` block, so an event uses the CasparCG this ZIP carries (below); nothing else needs to be installed or pointed at. No runtime download or global driver change is performed by this ZIP. Do not bypass production-window supervision with an always-on sender.
4. Run `Launch-PiRaiders.cmd` from the extracted root. Spaces/Unicode and `!` in its folder path are supported. The fixed entry uses only bundled Node. Missing machine config fails before SPX starts; invalid SPX config/occupied foreign port fails safely. Optional `Launch-PiRaiders.cmd --no-browser` still verifies owned startup and prints the credential-free numeric-loopback Game Day URL. Other arguments are refused. No executable, path or schedule is accepted from this command line.
5. Keep the launcher console running. Closing the browser tab leaves SPX alive for the application lifetime. Game Day preserves original SPX projects/rundowns and native HTML/OGraf controls in the separate SPX Graphics workspace. The iPad operator never sees this UI. Event sender lifetime belongs to the configured production window; Stop means black while that sender remains permitted, not application exit.
6. Ctrl+C, Ctrl+Break and closing the console window each request the same bounded shutdown/retry (Windows gives a closed console only a few seconds; the native job still closes what is left when the Node parent ends). The console close is tested on Linux with a real SIGHUP; its hosted-Windows proof is part 5d-2. Closing or killing the actual Node parent independently closes its native job, including descendants. A reported close failure retains unknown ownership and requires diagnosis before restarting. Native PIDs identify containment hosts; local process/readiness status is distinct from renderer output, source discovery, receiver connection and board routing. Private native stdout/stderr is discarded; the console uses fixed lifecycle/error categories plus the local controller URL.

## Source mode: setup and diagnostics (5f-1)

For an exchange source machine, copy `app/config/piraiders-app.source.example.json` (instead of the local example) to `app/config/piraiders-app.json` and replace every `<REPLACE: ...>` value (the exchange folder, ids and feed; CasparCG and the NDI runtime come from this ZIP, no path to set); the loader refuses the file while any is left. Store ids are new random v4 UUIDs, two different ones; the feed id and epoch come from the exchange, and the epoch is a plain number without quotes; `expectedCanonicalRoot` is the exchange folder's real full path. The design notes named below (`SOURCE_MACHINE_POLICY.md`, `EXCHANGE_SETUP.md`, `GAME_DAY_DIAGNOSTICS.md`) are in the source repository's `docs/design/`, not in this ZIP. Then, from the extracted root:

- `Setup-PiRaiders.cmd`: the setup command (`EXCHANGE_SETUP.md`): checks the machine file, the exchange folder and the feed, and makes the journal and approval list once. Safe to run again. It also reports whether this PC has the Microsoft x64 VC++ runtime CasparCG needs (`vcRuntime`) and, only when it is missing and you answer Y, runs the bundled `runtime\vcredist\VC_redist.x64.exe` (OPERATOR-CHECKLIST.md, step 4); nothing is downloaded. `Setup-PiRaiders.cmd --pin-offline`, with the application closed, pins prepared buttons for a cached start.
- `Diagnose-PiRaiders.cmd`: the diagnostics command (`GAME_DAY_DIAGNOSTICS.md`): store states without the application, runtime states from the running application or `APP_NOT_RUNNING`.

Both use only the bundled Node and the fixed `app/config/piraiders-app.json`, print one JSON line of fixed codes (no paths or ids) and exit 0 done, 1 refused, 2 wrong arguments. Windows CI runs both from the extracted ZIP in source mode against a synthetic exchange folder (part 5f-3); they are also tested on Linux.

## Bundled CasparCG, renderer and NDI (Q-020)

A machine file without a `caspar` block (both examples) uses the CasparCG the ZIP carries. When the app starts, it runs the bundled OpenGL 4.5 check (Setup and Diagnose print it as `graphics`) and chooses the renderer: `gpu` only when the check answers `GPU_OPENGL_45` under `"renderer": "auto"`, otherwise `software`; `"renderer": "gpu"` or `"software"` in the machine file forces either.

- `gpu`: the app starts `runtime\caspar\casparcg.exe` unchanged. No `opengl32.dll` sits beside it, so Windows loads the graphics driver's OpenGL.
- `software`: Mesa's `opengl32.dll` must never sit beside the Caspar that uses the graphics card, so the app makes its own copy once, `runtime-software\caspar\` beside `runtime\` (hard links where the disk allows them, else copies; Mesa's two x64 files beside that `casparcg.exe`), and starts that copy with the fixed software profile (`GALLIUM_DRIVER=llvmpipe`, `LIBGL_ALWAYS_SOFTWARE=1`, `MESA_GL_VERSION_OVERRIDE=4.5COMPAT`, only for the owned Caspar process). It is made again when the bundled files change. If it cannot be made, SPX and Game Day still run and a preparation is refused with `MESA_RUNTIME_MISSING`. This folder is yours, not the ZIP's: `Verify-PiRaiders.cmd` counts it as `extra`, so verify before the first launch.
- NDI: an NDI output without `runtimeDirectory` uses `runtime\ndi\Processing.NDI.Lib.x64.dll`. NDI® is a registered trademark of Vizrt NDI AB; more about NDI at https://ndi.video.

The Game Day page's Diagnostics panel shows **Graphics renderer** (`renderer: gpu` or `software`) and, beside the NDI sender, a link to ndi.video; `Diagnose-PiRaiders.cmd` prints `caspar` (`from`: `bundle` or `machine-file`, `renderer`, and `layout`: `ready`, `missing` or `not-needed` for the software copy; Diagnose never makes it).

The bundled Caspar starting from the extracted ZIP with the `software` renderer is shown on hosted Windows (Q-021, CI check `actual-extracted-full-app-private-ndi`). Not shown by any test yet: the `gpu` path on a PC with a graphics card (a manual check). On GitHub's hosted Windows runners there is no graphics card, so only `software` can be exercised there.

**Stadium warning: CasparCG's AMCP control port listens on every network interface.** The stock CasparCG 2.5.1 server binds its AMCP listener to all interfaces (`0.0.0.0`), not to this PC only; no setting in its configuration file changes that (`WINDOWS_OUTPUT_PROOF.md` › Security, in the source repository). Anyone who can reach this PC on that port while an event runs could send Caspar commands. Use the bundle only on a disposable, nonproduction PC on an isolated network until a reviewed fix or an approved firewall rule exists; do not install it on stadium equipment without the owner's approval and an off-air test.

## A machine file's own Caspar (optional)

A machine file may still name its own Caspar in a `caspar` block (`executable`, `cwd`); then the renderer choice is not applied and that Caspar runs as before. Such an explicitly prepared Caspar/Mesa installation can opt in to the tested software renderer by adding `"rendererProfile": "mesa-llvmpipe-compat"` inside the `caspar` object. This optional machine policy is not accepted from event catalog rows. Omit it to retain the existing inherited environment and component behavior. Unknown profiles and arbitrary environment maps are rejected.

The profile sets `GALLIUM_DRIVER=llvmpipe`, `LIBGL_ALWAYS_SOFTWARE=1` and `MESA_GL_VERSION_OVERRIDE=4.5COMPAT` only for the owned private Caspar process. SPX and legacy component launches retain their environment. Inherited case variants of these three variable names are replaced so Windows cannot choose a conflicting duplicate.

Preparation requires a nonempty regular `opengl32.dll` beside the canonical Caspar executable; putting a copy only in a different working directory is insufficient. A missing, empty, directory or symbolic-link library returns the fixed `MESA_RUNTIME_MISSING` boundary error before media staging, listeners or service startup. This presence check does not verify version/hash, loaded-driver identity, complete dependencies, pixels or hardware compatibility. Extracted-application output with this profile is hosted-Windows CI evidence (`actual-extracted-full-app-private-ndi`) only; target Windows10/stadium compatibility remains unverified.

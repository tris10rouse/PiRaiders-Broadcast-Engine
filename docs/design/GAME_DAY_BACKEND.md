# Next Game Day backend increment

Implementation plan from source review, 2026-11-15 UTC. This is a proposed implementation plan, not implemented behavior or evidence of Windows readiness. No tracked files, Git commands, lease operations or publishing were performed.

## Smallest coherent PR after sender-only ownership/shared admission

Add a trusted Node-only `GameDayManager` plus strict local machine/catalog parsing and real-filesystem tests. Do not add HTTP/UI or change the Windows launcher in this PR. The manager uses `createPreparedEventRuntime(compiledProfile,{manageSpx:false})` and its planned `dispatch(action)` facade, never `PresentationHost.dispatch()` directly. Test in an actual persistent SPX process in the following router/application PR; an independent Node HTTP process is useful narrower lifetime evidence but must retain that label.

Keep full standalone profile compatibility. Add a separate machine/catalog schema instead of letting browser or catalog entries provide the existing full executable-bearing prepared profile. Machine configuration is administrator-owned local data; catalog entries are local/manual event data. No Apps Script adapter, Google API, folder watcher or invented canonical Board identity is needed for this increment.

## Trusted APIs and ownership

Proposed module exports:

- `loadGameDayMachineConfig(file,{appRoot,nodeExecutable})`: bounded read, strict known keys/plain JSON, absolute resolved/frozen machine settings. Derive application executable and entry from trusted appRoot/nodeExecutable; do not accept them from catalog/HTTP.
- `createLocalEventCatalog(machine)`: async `list()` returns bounded sanitized descriptors only; `read(eventId)` returns a frozen compiled prepared profile plus sanitized descriptor/revision. Never expose raw path fields. Explicit refresh only initially.
- `createGameDayManager({catalog,runtimeFactory=createPreparedEventRuntime,clock=Date.now})`: trusted dependency injection only. Production constructor receives validated catalog. Factory never escapes a failed event preparation through SPX startup.
- Manager `listEvents()`, `snapshot()`, `prepare(eventId,{expectedSelection})`, `activate({expectedSelection,candidateId})`, `discardCandidate({expectedSelection,candidateId})`, `dispatch(action,{expectedSelection})`, `close()`.

Every manager mutation also carries the expected active catalog eventId (or null before first activation). Require BOTH that ID and `expectedSelection` to match before forwarding playback or replacing state; selecting the same event twice must still generate a fresh activation epoch. `expectedSelection` is a server-issued monotonically increasing safe integer identifying the active selection epoch, not a browser-chosen profile version. Reserve/increment it synchronously at activation/close before awaits. Candidate ID is a bounded opaque server-generated identifier separate from eventId and runtime's sender generation. A candidate’s source revision is the hash of the exact validated catalog bytes used to compile it; activation uses that frozen profile, not a silently re-read changed event file. Status revisions can be separate; avoid invalidating commands merely because a preparation progress message changed.

Only allow the fixed action set already in RossTalkSession: launch/next/previous/toggle-auto/auto/manual/reload/stop. `runtime.dispatch(action)` captures the exact current sender generation and delegates through `session.dispatch(action)` to the same bridge queue as TCP. UI requests must not synthesize TCP connections, claim an allowlisted sender, or bypass the shared admission path. The manager does not serialize playback behind a long prepare/close promise. Stop goes directly to the existing priority admission after synchronous selection checks, retaining its cancellation/orphan barriers. An aborted HTTP request must not remove an already accepted command or allow a successor around physically unsettled work.

Prepared runtime currently returns only start/snapshot/close. Shared-admission work must add dispatch without exposing session.origin/getProgramURL/producer cookie/token. Keep profile JSON strict: no dispatch callback, manageSpx, synthetic spawner, resolver or OS hook fields.

## Manager state machine and fences

Store at most one active record, one candidate, one actual preparation flight and one activation/close flight. Use immediate BUSY rejection for excess lifecycle operations rather than an unbounded operation queue. Each record owns exactly its runtime and immutable descriptor. Suggested public states: idle, preparing, prepared, activating, active, closing, faulted; snapshot includes sanitized active/candidate descriptors, operation flags, fixed lastError, expectedSelection, and existing redacted runtime status. Do not relabel prepared snapshot as renderer-ready or NDI sending. Receiver/board remain explicitly unverified.

Preparation invokes factory but not start: current factory stages/writes private local config without opening its RossTalk/presentation listeners or spawning processes until start(). A failed preparation retains active event and any still-valid accepted content. Dispose an old unused candidate successfully before replacing it. Never run a new initial preparation around an unresolved predecessor; current factory's initial stage has no cancellation option. A canceled/closed manager fences that result, retains the actual preparation promise, and closes any late-created runtime instead of publishing it. Do not pretend an AbortSignal physically stopped a resolver. Initial scope explicitly refuses prepare AND replace while the current event's production window (including prewarm) is allowed, or while any active/retired runtime snapshot reports preparing:true. Return fixed BUSY for physical-flight barriers and WINDOW_ACTIVE for the production policy. There is no background next-event preparation or new global staging service in this increment. Keep a strong reference to every closed runtime whose preparing:true survives close: close intentionally does not await ignored staging settlement. Recheck those retained snapshots before every later preparation/activation, and release the barrier only after actual preparing:false. Never clear the reference merely because close resolved, a signal aborted, the renderer was retired or window eligibility became false. The manager's own initial factory flight also remains a barrier until its physical promise settles, even after canceled preparation/manager close. This simple conservative admission preserves one actual decoder flight across event replacement.

Activation admission synchronously checks expectedSelection, candidate identity, manager lifecycle availability and current active production window using `senderAllowed(normalizeWindow(active.profile.productionWindow),clock())`. This includes prewarm, even if renderer is unready, source is offline, sender crashed or ordinary Stop is black. Do not use `ready` or presentation playing state as replacement permission. Initial activation when there is no active event can occur within that selected event's window, as intended.

Immediately before calling old.close(), recheck eligibility with no await between the check and reservation. Fence active commands first. Await confirmed old runtime close before invoking candidate.start(); then recheck its preparing flag and all retained physical-flight references. If any remain true, retain the closed old record as a barrier and prepared candidate as inactive, return BUSY and admit no candidate.start until actual settlement. Never bind a second RossTalk/presentation listener or create a second sender while close is pending/failed or an old physical staging flight survives. On old close failure retain its record, block activation, expose CLOSE_FAILED and allow retry. Do not clear the old reference and assume window expiry killed it. On candidate start failure, retain that candidate until its cleanup is confirmed; a failed cleanup likewise blocks replacement. Explicit Stop only sends black and must never call runtime.close or change selection.

Manager close is synchronous admission/fencing followed by actual owned cleanup. Start active.close immediately; do not wait for candidate preparation to settle before requesting sender shutdown. Late preparation disposal can continue under the held flight. Decide whether returned close awaits that flight separately from application native-kill safety: do not let an uncooperative preparation delay parent SPX JobHost termination. No manager operation may stop application SPX.

## Machine configuration and local catalog

Proposed schema1 machine fields: `spxConfigFile` (safe app-root relative), `catalogDirectory`, `mediaRoot`, `cacheRoot`, `runtimeRoot`, fixed `caspar:{executable,cwd}`, fixed `output:{type:'none'}` or explicit NDI name/runtimeDirectory, fixed `presentation:{port}`, and fixed `rossTalk` host/port/allowedSenders/commandMap. Node executable, SPX server.js entry and app cwd are derived by the launcher. SPX port comes from the actual selected SPX config; do not maintain a second conflicting browser port. Output-none is explicit; never silently fall back from missing NDI to none.

Proposed catalog entry: schemaVersion1/provider local-manual/eventId/displayName/productionWindow/relativeSourcePath/playback/startup. The compiler supplies machine-owned executable/output/control fields and a cache/runtime subtree derived from eventId. EventId uses existing bounded lowercase-hyphen grammar and must match `<eventId>.json` exactly. Treat displayName as bounded plain text, not HTML. Default production prewarm and playback settings stay the existing validated defaults, without double-applying prewarm.

Startup source is explicit. Cached startup references only a bounded snapshot UUID under that event's cache, never an arbitrary supplied path. Existing media snapshots are UUID directories (media-snapshot.cjs), not content hashes. Return cached choices only from validated owned cache inventories; no arbitrary browser path is accepted. Canonical membership/full load still happen in PreparedEventRuntime. Offline cached startup must not consult mediaRoot/relative source through realpath/stat; lexical source confinement is compiled separately, and async source alias checks occur only for source prepare/Reload. This preserves disconnected Drive startup.

Suggested routine bounds: <=128 catalog entries, <=64KiB JSON file, bounded displayName128 characters. Reject traversal/separators/colon/controls in event IDs and unsafe relative source segments; enforce canonical catalog-file containment and reject symlink/reparse traversal, duplicate/case-colliding IDs and nonregular entries. Reject unknown fields and arbitrary executable/XML/producer URL overrides. Catalogue listing should identify malformed entries using bounded ID/fixed status where possible, without allowing a bad file to prevent actual SPX startup or exposing absolute paths/raw errors. Read each selected file boundedly and detect mutation during read. These are new local/manual schema decisions, not an assertion of Apps Script compatibility.

Do not overwrite config.json/DATAROOT or fix upstream's logfolder/dataroot typo as incidental scope.

Insert a Game Day namespace guard before statics/parsers/CORS for every case/trailing-slash/path variant that Express will accept; mount actual new router after sessions and before broader SPX application router. Guard should prevent accidental static shadowing/CORS grants, set no-store/referrer/CSP/frame policy for new responses, and return fixed namespace errors. Never globally alter SPX CORS/auth/routes to enable Game Day.

`spxAuth.CheckLogin` allows config without username as session user default; username with empty password renders an auth-policy page; configured credentials require matching session user, otherwise redirects to /login. Reuse its page semantics for GET /game-day; API authorization should enforce the same existing authenticated-user policy with fixed JSON401/403 (not follow a login HTML response as command success). Mutations require JSON, exact numeric-loopback Host/Origin, loopback socket peer, checked Fetch Metadata, constant-time per-session CSRF. Existing CheckAPIKey is a distinct API-key policy and must not substitute for browser session/CSRF. Do not trust forwarded headers or leak catalog/path/config through unauthenticated state. The static SPX session secret means new CSRF token must be unpredictable per actual stored session, never derived from the signed cookie or hardcoded secret. Game Day browser must never navigate/embed the private producer origin, which could consume the sole Caspar renderer session.

`Launch-PiRaiders.cmd` currently invokes only piraiders-launcher.cjs with config/piraiders-launcher.json. Legacy loadSettings requires exactly SPX+Caspar services and one event window; it cannot serve as the persistent app supervisor. New `scripts/piraiders-app.cjs` should use a standalone ProcessSupervisor with one actual SPX spec and endpoint diagnostics, independent of event windows. Pass opt-in app-config via an explicitly documented trusted environment variable to actual server.js; do not change its first config argv contract. Suppress inherited SPX launchBrowser only in explicit app mode in memory to avoid duplicate LAN browser launch; leave stored config/upstream mode intact.

Parent shutdown must immediately terminate its owned SPX JobHost regardless of manager preparation. Windows nested containment of SPX→event JobHost→Caspar must be tested on actual Windows; current tests prove isolated hosts, not this complete nested topology. Do not add an insecure browser shutdown endpoint or assume SIGTERM gives Windows graceful cleanup. Existing JobHost kill-on-close tree ownership is the fail-safe. A graceful manager-close handshake can be a subsequent bounded enhancement; it must never gate native termination.

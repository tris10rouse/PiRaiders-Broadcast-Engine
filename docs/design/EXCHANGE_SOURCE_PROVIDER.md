# Explicit exchange provider/runtime bridge (BE-006)

Trusted backend implementation. The Game Day manager enforces mandatory branded admission; default machine/catalog/web selection remains local-manual. No default machine/catalog/web/frontend integration, source writes, journal initialization/rebinding, installs, Git/GitHub/lease changes or native output changes were performed here. Unchanged dependency copies, fixtures/templates and node_modules symlink are execution support, not publication candidates.

Success criteria follow ROADMAP Stage3/4 and BE-005/BE-006: an explicit ordered source provider can prepare and feed an immutable verified schema2 deck to the existing runtime; accepted playback survives source failures/ineligibility; online candidate admission is separate from active control/window; offline cached construction requires trusted approval; logical cancellation never releases physical preparation ownership early. Tests use real metadata/journals/cache/image decoders/session TCP+HTTP+WebSocket, with explicitly synthetic native process and renderer ACK boundaries. They do not establish Caspar/CEF/NDI/hardware compatibility.

## API and authority

`createExchangeSourceProvider({providerId,sourceRoot,cacheDir,journalDir,storeId,binding:{feedId,epoch},timeoutMs?}, trustedTestDependencies?)` requires approved machine-owned roots and an existing explicitly bound journal. Default coordinator timeout is60000ms, within its existing10..60000 cap. The provider lazily owns one coordinator, serializes online, offline and verification operations, and rejects a second live owner with overlapping configured source/cache/journal paths. Before each operation it also claims the observed canonical local cache/journal roots, so a second configured alias cannot bypass the live owner; this local resolution requires no Drive access. Actual source/private canonical separation is checked online before initial cache/runtime work. Per-profile private roots are checked without symlink traversal. Runtime independently checks canonical cache/runtime separation.

Methods are `createPreparedMedia(profile,{authorizeOffline?})`, metadata-only `inspectSelection(tuple)`/`refreshCatalog()`, fixed path-free `snapshot()`, and `close()`. Only branded preparedMedia drivers stage; no HTTP/UI stage API is installed. Multiple profile/selection drivers share the same physical provider owner. Driver close cancels only its own use, not a replacement's shared provider. Provider close fences all tokens and retains ownership until the actual operation drains. In-process ownership is not a cross-process or hostile-filesystem lock; existing journal CAS/immutable publication and Windows canonical checks remain the durable boundaries.

An explicit source profile keeps schemaVersion1 and common machine-owned executable/window/output/RossTalk fields, with outer `provider:'exchange-v1'` and:

```
media: {
  provider:'exchange-ordered-v1', providerId, binding:{feedId,epoch},
  identityTuple:[schoolYear,eventKey,boardKey,origin,buttonIdentity], cacheDir,
  startup:{mode:'source'}
  // OR startup:{mode:'cached',snapshotId:<UUID>,playbackFingerprint:<SHA256>}
}
```

`eventId` stays an opaque machine-owned engine slug; it is not a lossy conversion of the source tuple or permission to reuse local-manual listing semantics. Source root/journal/store identity live in the provider's machine config, never source manifest/profile data. The driver is WeakMap-branded to the exact normalized profile, including its confirmed window and machine policy. Source runtime construction rejects a missing/copied/wrong-profile driver; local-manual runtime rejects driver injection. Profile JSON cannot carry callbacks or lexical source paths for an exchange source. Legacy local-manual/local-lexical-v1 validation and behavior remain intact.

Drivers provide `initial`, `resolveReload({signal,acceptedSnapshot})`, `admissionToken`, `canCommitPreparedSnapshot`, and `close`. Runtime has a trusted source-only `candidateAdmissionToken()` method. `admitExchangeCandidate(token,expectedProfile?)` is a synchronous, passive, no-I/O exported helper; root manager should pass its exact normalized profile. Tokens contain only a fixed kind and are verified through a private WeakMap; cloning/freezing arbitrary JSON cannot grant admission. Admission requires the real owner's binding/store checks, successfully verified initial cache, exact profile, latest matching healthy eligible completed selected observation and open driver/provider. A retained coordinator lastAccepted pin alone is insufficient after an unavailable observation. Provider busy also denies new candidate admission. Source runtime rechecks once before its first `start()`. The manager separately rechecks before publication, old retirement/new start and acknowledgement, and after optional synchronous policy callbacks. Optional approval cannot override the mandatory source brand.

The supplied productionWindow is an externally confirmed trusted backend input, not copied automatically from a source proposal. This increment does not persist approval records or implement their UI. Once start is authorized, the window/native cutoff is sticky through future prewarm and sender restarts. Fresh source metadata never enters active canControl/launcher.allowed, never blacks an already active event, never edits or extends its confirmed window. No source Button->RossTalk/GPI mapping is introduced.

## Initial content, Reload and changed render admission

Online initial preparation goes through the real coordinator, requires eligible content preparation, then independently loads/verifies schema2 cache and provenance against the exact provider binding/tuple/fingerprint before runtime-directory writes. Runtime starts no listener/process until explicit start. Source omission/invalidity/ineligibility/journal errors cannot cause lexical fallback.

Reload first inspects verified metadata for the pinned tuple. If its verified playback fingerprint equals the ACTUAL runtime accepted snapshot, the driver offline-verifies and returns that accepted snapshot's exact path. Coordinator.lastPrepared is only a content-cache reference and may be a different unactivated/ineligible selection version. Regression A(active)->C(content-only/ineligible cache)->A(metadata/assetKey renumbering, source A assets absent) returns accepted A; it does not require source assets or create an unnecessary A UUID. The existing host verifies the same immutable UUID/deck and acknowledges without replaceDeck/index/mode/Auto timer reset. Source ineligibility does not prevent acknowledgement of identical already accepted playback.

Changed Reload inspects eligibility, performs a new fresh coordinator capture/preparation, rechecks that later result rather than attaching the earlier inspect receipt, and verifies its schema2 cache. If the later result returns to accepted playback, it again returns the verified accepted path. A changed ineligible/empty/incomplete/unavailable selection declines replacement and preserves last-good output. Accepted runtime media updates only when the actual controller deck ID matches the prepared candidate after render commit, using existing syncAccepted ownership.

Each changed prepared object has a private issuance proof binding driver, fresh observation, candidate fingerprint and actual accepted path/fingerprint. Runtime supplies a canCommitPreparedSnapshot callback through the session to the host. After full host verification, same-UUID no-op bypasses changed admission; a changed candidate must pass the callback. The host then passes the callback into the queued controller replaceDeck request. A held Auto/render queue cannot make an earlier check authoritative: the controller invokes it synchronously at the changed renderer dispatch boundary, before changing its deck/index or clearing the Auto timer. Stopped replacement checks before mutation too. Both branches recheck close, Stop, generation and abort after the trusted callback; returning true after cancelling the request cannot install or render its deck. Only literal true admits; false, exceptions, truthy objects and Promises deny (rejected Promises are consumed) with ADMISSION_DENIED and no Stop/black. Legacy calls without a guard retain their default behavior.

That synchronous changed-render dispatch is the commit admission boundary. Source observations AFTER the boundary do not attempt to undo an already dispatched/painted frame; there is no atomic Drive snapshot or rollback claim. Ordinary Stop, native expiry, renderer/session generation fences and cancellation retain their existing authority.

## Physical ownership and budgets

The raw coordinator may settle abort/timeout while actual handle close, stage cleanup, decoder work or journal I/O remains pending. The provider wrapper always waits for coordinator.snapshot().busy to drain before settling its stage/catalog-style promise. Runtime's existing flight therefore remains true through actual cleanup, and manager's existing initial-preparation flight can retain factory/catalog ownership. Logical runtime close requests native cleanup promptly; retired runtime.preparing remains true until the ignored preparation wrapper settles. Late results cannot commit. Shared provider ownership cannot be discarded/recreated around that orphan. Manager remains responsible for the shared cross-provider barrier, including legacy decoder work; source preparation is not exposed outside that trusted lifecycle path.

Every driver operation gets one immutable110000ms monotonic deadline covering inspect, fresh prepare and cache verification. Each constituent coordinator attempt keeps its existing<=60000ms cap. Signals/deadline fences are checked after awaited work and before acknowledgement. Physical drain is intentionally not timed away; an orphan may remain busy beyond the logical deadline. Default runtime source sessions explicitly use resolverTimeoutMs120000 and host prepareTimeoutMs60000, both within existing validation caps. With the unchanged command default12000, the session derives218500ms bridge handler budget, under its existing300000 cap. Local-manual defaults remain unchanged. These are bounded backend budgets, not elapsed-time guarantees. A meaningful test holds staging5.25s and still succeeds, proving the old automatic5s resolver timeout is not silently inherited. Schema2 persistent-decoder optimization is a separate prerequisite/performance increment owned by root; this candidate does not relax product asset limits or coordinator caps.

## Offline mode

Offline cached construction defaults deny. It requires an explicit trusted synchronous authorizeOffline callback returning literal true, checked before and after load and again by the candidate admission helper. The callback receives a frozen path-free provider/store/binding/tuple/window/UUID/fingerprint context and must represent externally approved machine/private-root/window policy; a Promise or truthy value is not approval. The local journal is opened with the separately retained store UUID and exact approved binding; the exact cache UUID is loaded with full schema2 hash/decode/provenance verification. No automatic journal setup, rebind or cached-content authenticity beyond these local boundaries is claimed.

Offline construction never stats/realpaths/opens sourceRoot or creates/uses the online coordinator. Source paths are only lexically checked; local cache/journal/runtime paths are canonicalized and checked for links/overlap. Because Drive is deliberately absent, offline mode cannot revalidate an unknown source alias against private roots. The trusted external authorization must carry prior machine-approved canonical-root context. It cannot claim current source eligibility. Up to2048 registered selection identities are retained independently of healthy observations. A refresh invalidates offline-only drivers after cancellation, omission or catalog failure without inventing a healthy selected pin. Offline authorizers are followed by lifecycle/operation/observation rechecks. Known invalidating observations revoke new offline admission; active recovery continues under already retained window authorization. Persistence and operator approval UI remain outside this backend API.

# Awaited Game Day candidate admission (BE-006)

The manager can now await a trusted approval refresh before publishing a prepared candidate, retiring an old event, starting its replacement, and acknowledging activation. This is a lifecycle boundary for the PC source service; it does not implement the service, approve source data, expose a web permission, or change active playback policy.

`createGameDayManager({...,refreshAdmission})` accepts an optional trusted function with the same frozen `{profile,descriptor,revision,admissionToken}` context as synchronous `admitCandidate`. Only an awaited literal `true` permits progression. Throws, rejection, missing results and truthy nonbooleans deny. Source branding and synchronous policy remain mandatory and cannot be overridden by this callback. No callback can arrive through machine/profile/source/HTTP JSON.

The refresh helper owns the actual asynchronous work and returns only its decision. The caller checks its current generation/closed state and performs passive source/policy admission after the await. Window/snapshot callbacks are also fenced; the final synchronous check immediately precedes candidate publication, old retirement and new start on the source/new-hook path. Final window policy runs before the last admission check preceding active acknowledgement. Freshness is checked again before mutations, including candidate removal after awaited cleanup. There is no added await or changed callback count for the no-hook local/manual path.

A separate physical refresh reservation keeps `snapshot().physicalBarrier` true until the actual callback settles, even after logical CLOSED. Close starts native/runtime cleanup promptly and can settle its public result without waiting for an uncooperative approval read. The operation/factory reservation remains until physical work drains. A late callback cannot publish/start or clear a closed manager's retained candidate pointer. No watchdog releases actual ownership early; trusted integration must supply bounded I/O and must not discard/recreate an owner around unresolved work.

Active commands and priority Stop never invoke candidate refresh/admission. Persisted revocation, source eligibility changes or a missing approval directory cannot change an already active confirmed window or request black through this seam. Native sender cutoff remains independent. The new hook retains the old immutable window across its extra awaits: if old prewarm begins after retirement or during post-start refresh, the new candidate is declined/cleaned before acknowledgement. No rollback or automatic restart of the old runtime is claimed.

Exchange candidate labels accept200 Unicode codepoints with a400-UTF16 quick bound; local/manual labels and flat listing retain128 UTF16 units and128 entries. Source identity is not derived from a display label, and this change does not turn the flat local catalog into the hierarchical source selector.

## Review and executed evidence

The initial candidate's passive check inside the async helper was too early. A genuine source driver was revoked in a queued microtask after that check but before the caller resumed; activation incorrectly succeeded. Another queued close invoked passive policy after manager closure. Both were reproduced before caller-side freshness/admission checks fixed them.

Further independent/root review reproduced final-clock source revocation, late cleanup clearing a closed candidate, and source revocation during policy/snapshot callbacks before publication/retirement/start. The fixes keep all current boundary checks synchronous after the relevant callbacks, with freshness before lifecycle mutation. This is observed cooperative lifecycle safety, not an atomic transaction against arbitrary hostile clock or policy implementations.

Revocation is written while synthetic start is held; the post-start refresh rereads it, denies acknowledgement and closes the candidate while retaining cache. A second case removes the approval directory after activation and verifies active Next/Stop perform no approval reads and preserve the confirmed window. Native runtime boundaries in these focused tests are synthetic; they establish no native Windows/output compatibility.

No frontend/rendering changes occur here, so there are no new screenshots or whole-surface UI claims. Final full regression and final-SHA Windows/output evidence are recorded in the PR.
